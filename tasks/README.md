| 19 | Payload schema (versioned) + `Publisher`: serialize → AES-GCM encrypt → publish → **read back**, with a `publication` audit row | 17 | BLOCKED | The Mac↔phone contract. Carries `published_at`, `publish_interval_seconds`, `grace_seconds` and a monotonic `seq`; `schema_version`, `pairing_id`, `seq` and `published_at` go in the AAD. **The payload contract carries the total's age as the tagged `(age_state, as_of)` of task 14** — `as_of` present *only* when `age_state = KNOWN` — plus `static_account_count`; a schema that lets a caller read a bare date is the bug this contract exists to prevent. **`seq` is never reset across pairings** (§6.3.1), so a payload from an earlier pairing can never present a higher `seq` than the current one. Every publish is followed by a **read-back** asserting the transport serves the `seq` just written, recorded as **tri-state `publication.readback_state` (`OK` / `MISMATCH` / `UNAVAILABLE`)** plus `readback_attempts`/`readback_seq` (§9.3). `MISMATCH` is the integrity alert; `UNAVAILABLE` (retried 3× over ~30s) is transport health and **must not** raise the integrity alert — a failed request is not evidence of a wrong value, and merging the two would make the tamper signal fire on ordinary network weather until nobody read it. It costs one request a day and is the Mac-observable half of transport integrity. **Rev 6 — a read-back alone cannot see a rollback *between* publications**, because the Mac's own next `PUT` overwrites the restored value before any read (§9.3). So `Publisher` also **reads before it writes**, recording `prewrite_state` (`MATCH` / `ROLLBACK` / `FOREIGN` / `ABSENT` / `UNAVAILABLE`) and `prewrite_seq`. **Rev 7 — what it compares against is the whole difficulty, and rev 6 got it wrong: not the last `publication` row.** That table records *attempts*, including failed ones, and `rotate`/`revoke` delete the snapshot on purpose — so rev 6's rule classified a harmlessly failed write as `ROLLBACK`, every rotation as an unexplained deletion, and a `PUT` whose response was lost as `FOREIGN` (the gravest state, aimed at the Mac's own write). Required mechanics: (a) `publication.outcome` is **`LANDED | UNCONFIRMED`** — a 2xx is the only confirmation, and a timeout, a dropped connection and any non-2xx all stay `UNCONFIRMED`, because "did not apply" and "applied, answer lost" are not distinguishable here; (b) the comparison basis is the **expected-live set** of §9.3 — the newest `LANDED` publication *plus every `UNCONFIRMED` attempt after it*, or `ABSENT` after a successful local `rotate`/`revoke` or before the first publication; (c) provenance is byte-level — `payload_sha256 = SHA-256(nonce ‖ ciphertext)` over the **AEAD output, not the JSON envelope** (§8.4.2's whitespace trap), and an object is ours iff the **pair** `(seq, payload_sha256)` matches a local row, so our own ciphertext re-declared under a different `seq` is `FOREIGN`; (d) the attempt row is written **before the request is sent**, or a crash in between leaves the Mac unable to recognise its own write; (e) a pre-write read **resolves** the `UNCONFIRMED` rows it settles, so the set collapses back to one element. Acceptance criteria: the failure states stay **distinct** (`ROLLBACK` is the §6.2.2 restore signal; `FOREIGN` means something that is not this Mac wrote to our object — **not** "the write token leaked", since a control-plane holder needs no token; `ABSENT` alerts only when unexplained; `UNAVAILABLE` is transport health and **must not** raise integrity); a `ROLLBACK` **still publishes** afterwards, because the number has to keep moving; and the tests cover all five timelines: a **known-failed write** (next read sees the previous object → `MATCH`, not `ROLLBACK`), an **unconfirmed write that did land** (→ `MATCH`, row resolves to `LANDED`, never `FOREIGN`), an **unconfirmed write that did not land** (→ `MATCH` against the previous, row resolves), a **normal rotate/revoke deletion** (→ `MATCH` on absence, no alert), a **real rollback** (publish 100 → external restore to 99 → next tick observes 99 before writing 101 → `ROLLBACK`), and **unrecognised content** (→ `FOREIGN`). The one indistinguishable case — a restore to the *immediately previous* publication landing inside a lost-response gap, read as a write that never applied — is documented in §9.3 and must be reproduced as a test asserting the *documented* reading, so a future change cannot flip it silently. No new route — `GET /snapshot` already accepts the write token. Ciphertext only ever leaves the machine, whatever transport 20 picks. |
